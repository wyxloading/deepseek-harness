# Agent Note: DeepSeek routes refresh their model catalog from the endpoint

Status: implemented

[English](2026-09-14-deepseek-endpoint-model-refresh.md) | 中文

## Problem

把 DeepSeek 线路指向自有代理或网关的部署，需要手工维护该线路的提示性模型目录。这个目录正是「模型」页与模型选择器展示的内容，因此随着网关新增、改名或下线模型，它会逐渐漂移，而设置界面上没有任何入口可以询问端点实际提供什么。pi-ai 适配器族已经通过 `llm/discoverModels` 回答了这个问题；直接 DeepSeek 适配器从未注册模型发现，因此它的行没有获取动作。

这项能力缺失也正是插件无法提供该动作的原因：「模型」分区的 `settings.models.provider-card` 座位本就是为仓库外的 UI 准备的，但只有当拥有该线路的适配器族愿意应答询问时，卡片才能提供获取。

## Decision

DeepSeek 插件为自己的设置命名空间注册模型发现，并由一个新的客户端包贡献使用它的卡片。

`llm-deepseek` 在 apply 期间注册 `ctx.llm.registerModelDiscovery('llm-deepseek', ...)`——即[草稿端点记录](../architecture/2026-08-04-draft-provider-endpoint-interrogation.zh.md)所定义的 seam 在第二个适配器族上的应用。注册从适配器使用的同一套按请求解析的事实中取得端点与凭据，因此询问针对的是线路当前的端点，而不是某份存储副本；请求携带的 `baseURL` 或一次性 `apiKey` 可以为草稿覆盖它。凭据按可选方式解析：部署未提供该引用时以未认证方式探测，因为私有网络中的网关可能应答公开列表，而在询问之前就拒绝会掩盖这一点。

询问发起 `GET {baseURL}/models`，读取 DeepSeek 线上方言使用的 OpenAI 兼容列表——`data` 数组，或某些网关用以替代它的增强 `models` 映射。普通 `display_name`/`max_input_tokens`/`max_tokens` 拼写，以及网关使用的驼峰与 `limit` 拼写都会被读取；没有可用 id 的条目会被跳过，而不是让整个应答失败。应答只是候选项元数据：该模块不读取也不写入任何设置。

`@deepseek-ai/dsh-client-ui-settings-models-refresh` 以 `llm-deepseek` 为 key，向「模型」分区带 key 的 `settings.models.provider-card` 座位注册一张卡片。卡片通过客户端 settings scope 读取线路当前目录，向 `llm/discoverModels` 索取候选项，并打开一个选择器，其中列出的每个模型默认勾选。确认时会写入一个替换 `models` 的 `settings.mutate` 路径操作，并以卡片读到的命名空间修订号作为栅栏；这是本包唯一的写入。线路原本就有的模型会保留已存储的行，因此用户调整过的显示名称或容量会在刷新后存续，而未勾选的模型会离开目录。

## Alternatives considered

**把卡片放进 `ui-settings-models`。** 「模型」页已经拥有带获取动作的模型列表编辑器，在那里加一个按钮的代码量比新建包更少。它落选是因为扩展座位与发现注册表的存在本身就是为了让页面之外的配置界面来做这件事：否则页面必须了解 DeepSeek 命名空间，而承载卡片的包也不再是独立单元。

**由新插件的 Host 半边注册发现。** 插件可以为任意设置命名空间注册发现，因此适配器包无需改动。它落选是因为端点与凭据解析必须重新实现：`llm-deepseek` 通过自己的设置分节与启动环境解析 `baseURL`，并通过凭据 seam 及其环境回退解析凭据。这些规则的第二份实现就是"哪个端点是已配置的"的第二个答案，两者会逐渐漂移。

**改由浏览器直接获取。** 页面与本地网关可以同主机，因此直接 `fetch` 看起来等价。它落选是因为浏览器完全无法读取 secret 角色的凭据，而端点对 GUI 而言又是跨源的；Host 已经同时拥有这两个事实。

**自动应用获取到的列表。** 一次点击就可以不经选择器直接写入目录。它落选是因为设置文档才是决定线路提供什么的唯一依据，静默重写会丢掉用户有意保留的模型或覆盖他们修正过的容量。选择器把采纳保留为显式选择，与 pi-ai 编辑器"发现应答只是候选项、从不是配置"的规则一致。

## Consequences

「模型」页在 DeepSeek 行下方多出一个按钮，让目录与该线路解析到的端点（包括部署自有网关）保持一致。它写入的目录是提示性元数据：没有任何请求会据此校验，发现路径也从不进入提供方推理请求。

本包在 Host 侧是惰性的，因此除构建外不带任何 Host 依赖；询问契约留在适配器族中，未来某个族要加入自己的实现也在那里。现在"这个端点提供哪些模型"有两个答案——适配器自己的列表读取器与 pi-ai 的读取器——它们保持分离，因为两个包服务于不同的线上方言，且都不对外导出可复用的读取器。未组装设置提供方或 `llm` 服务的部署不会渲染卡片，而未注册模型发现的线路会被座位的 key 跳过，且不报错。

## Testing

适配器的发现由单元测试固定：列表读取器容忍的方言与边界情形，以及在真实 HTTP 服务器上验证凭据选择、拒绝、超大与流式应答、非 JSON 应答和取消。客户端包由以下测试固定：控制器的投影、采纳合并与两种 Remote 结果；卡片的按钮、选择器筛选、全选、采纳、拒绝上报与只读禁用态；以及一次 apply 测试，覆盖注册、其语言字典、触及两个 Remote 的 inject 面，以及贡献随 fiber 一同卸载。
